# {Brand} PRD 조사 공통 규격 (에이전트용)

## 대상 시스템
**{Brand}**(가칭) — 인포그래픽 "{원제} — *{핵심 문구}*"({원저작자})의 **{N} 레이어 × {M} 개념(+누락 보완 {X})** 을 그대로 제품 구조로 옮긴 **{제품 성격}**.
- 도식 각 카드 안 **세부 항목**(예: {카드A} 의 {항목1}·{항목2}…)을 가능한 한 잘게 나눠 **개별 에이전트(마이크로 에이전트)** 로 만든다.
  각 에이전트는 **개별·독립 구동 및 배포**(컨테이너/단일 바이너리/패키지, A2A 엔드포인트 + Agent Card 노출)가 가능해야 한다.
- 에이전트를 **등록·수정·삭제·배포·버전·롤백·모니터링** 하는 **Agent Manager**(오케스트레이터 포함 Multi-Agent System 관리면)도 독립 구동·배포 가능.
- 멀티테넌트: 기업(조직)·프로젝트·사용자·역할(RBAC), 테넌트별 키·예산·정책·데이터 격리.
- 콘솔 UI 는 도식 레이아웃(레이어 띠 + 번호 카드 + 카드 내 흐름도/아이콘 타일 + 하단 띠)을 정보 구조로 그대로 따른다.
- 설치 패키지는 멀티플랫폼(Linux/macOS/Windows, amd64/arm64), 릴리스 방법(버전·채널·서명·SBOM)까지 정의.
- [요청문의 추가 요구 — 1~6항, *, ** 를 원문 요약으로 나열]

## 입력 자료 (반드시 먼저 읽을 것)
- `research/_INPUTS.md` — 입력 인벤토리와 입력별 전사·요약(분석 보고서 · 요구사항/개발방향 문서 · 첨부 이미지 · 참고 사이트 · GitHub URL · 요청문), 입력 간 충돌·결정.
- `research/req_items.tsv` — 요구 항목 RQ-NNN(유형 fr·ui·nfr·constraint·goal·non-goal·info, 우선순위, 원문). **담당 단위와 관련된 RQ 를 전부** FR 로 옮긴다.
- 분석 보고서가 입력이면 `{기초 보고서 _assets}/research/` 의 r1~rN(개념별 조사) — 도출된 오픈소스 스택은 **모두** 참고 대상. 원본 도식: `source_infographic.png`.
- 첨부 이미지는 `inputs/IN-NN.*` (Read 로 직접 본다), 참고 사이트 발췌는 `inputs/IN-NN.txt`(부족하면 WebFetch).

## 산출 형식 (research/rN_*.md, 한국어)
1. `## 1. 원조 개념 분석` — 담당 개념의 도식 원문(카드 문구·흐름·타일) 전사와 분석 보고서 요약, 세부 항목별 책임 정의. 모든 사실에 출처(URL 또는 보고서 파일명).
2. `## 2. 대체·유사 시스템` — 상용·오픈소스 대안 **최소 12종**: | 이름 | 구분(상용/OSS) | 핵심 기능 | 라이선스·가격 | 연동/API | URL |. OSS 는 owner/repo 명기.
3. `## 3. 기능 매트릭스` — 행=세부 기능(20~40개), 열=주요 도구 6~8개, 값 ●/◐/○. 표 아래 "대부분 제품이 비워 둔 기능" 3~5개.
4. `## 4. FR 후보` — 단위 ID 마다 `### <단위 ID> <에이전트명>` + 표: | ID | 이름 | 하는 일 | 구현 요지 | 우선순위 | 참고 OSS | 근거 |.
   - ID `FR-<단위ID>-NN`, 단위당 **5~10개**. 도식의 카드 문구·불릿·흐름의 모든 요소가 최소 하나의 FR 로 이어져야 함.
   - 하는 일 = 사용자/운영자 관점 1~2문장. 구현 요지 = 라이브러리·API·알고리즘·데이터 구조·설정 키까지 구체(그대로 개발 가능). 우선순위 P0/P1/P2(RQ 의 우선순위를 따른다). 참고 OSS = owner/repo 를 ` · ` 로 구분.
   - **근거 = 이 FR 이 나온 RQ-ID·IN-ID·도식 요소**(예: `RQ-012 · IN-03 도식 카드 04`). RQ 매핑은 이 열로 자동 추적되므로 반드시 적는다. FR 이 아닌 곳으로 가는 RQ(NFR·제약)는 research/req_map.tsv 에 적는다.
   - 셀 안 `|` 금지(필요하면 `/`), 줄바꿈 금지.
5. `## 5. 컴포넌트·데이터` — 에이전트 명세 표: | 단위 ID | 입력 | 출력 | A2A skill id | 주요 설정 키 | 발행/구독 이벤트 | 독립 배포 형태 |, 주요 엔터티/필드, 계약 JSON 예 1개(40줄 이하).
6. `## 6. UI/UX 참고` — 담당 개념의 콘솔 화면 구성안(영역별: 좌 내비/중앙/우 패널/하단)과 핵심 상호작용 8~12개, 도식 흐름도·타일을 화면에 옮기는 방법, 레퍼런스 제품 패턴. 텍스트로만.
7. `## 7. 동향·리스크` — 2025~2026 동향(수치는 출처), 라이선스·보안 리스크, [미확인] 사항.
8. `## REPOS` — 한 줄 하나: `owner/repo | 역할(한국어 짧게) | 결합방식 | 비고`. 결합방식: E=내장(허용적) / A=별도 프로세스·컨테이너(GPL/AGPL/ELv2 무수정) / L=연계만(API) / R=패턴 참고 / X=제외·대체.
   반드시 `gh api repos/owner/repo --jq '.full_name+" "+(.license.spdx_id//"NONE")+" "+(.stargazers_count|tostring)+" "+(.archived|tostring)'` 로 실재·라이선스·아카이브 확인한 것만. 25~60개.
9. `## SOURCES` — 참고한 URL 전부(한 줄 하나).

## 규칙
- 확인 못 한 것은 `[미확인]`, 업계 일반 지식 기반 가정은 `[도메인]`. 가격·수치는 조사 시점 기준.
- 라이선스는 SPDX. AGPL/SSPL/BUSL/ELv2/비상업은 반드시 경고.
- 이미지·코드 복제 금지. 기능·구조만.
- 장황한 서술 대신 표·글머리. 파일 분량 700~1,200행. **`## ` 절 하나 끝날 때마다 파일에 저장**.
- 사용자 GitHub({user}) 스타 목록: research/stars_all.tsv (full_name, stars, license, lang, desc, archived, starred_at) — 관련 항목을 grep 으로 찾아 우선 참고하고 REPOS 비고에 `★user` 표기.
  사용자 저장소 목록: research/user_repos.tsv (name, fork, archived, lang, license, pushed, stars, visibility, desc) — 재사용 후보는 비고에 `own`.
- 출력 폴더(`{root}/Need-to-be-organized-into-PRD/` 또는 `{root}/`)의 다른 PRD·화면설계서는 **형식 참고용일 뿐 출처로 쓰지 말 것.**
- 참고 사이트·캡처는 기능·정보 구조·UI 패턴만 참고(문구·이미지 복제 금지), URL·접근일을 SOURCES 에 남긴다.
